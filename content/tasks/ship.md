# 上线一个别人能用的版本

## 为什么做

代码生成后，环境、配置和维护仍是交付的一部分。本指南保持静态；你学习构建的业务产品是否需服务端，按实际功能决定。

## 开始条件

核心流程和必要检查已通过；明确交付物。

## 学习要点

- 配置与环境：能复现的构建与启动命令，加上必需的配置项清单。配置从环境变量注入，不写进公开仓库；换一台机器照文档能跑起来，才叫可复现。
- 静态/服务端部署：静态托管只返回文件，不会运行你自己的服务端程序，也不适合藏密钥；需要持久化数据或密钥时，必须选支持服务端的环境。
- 版本与恢复：版本要能确认（commit 号或构建号）；恢复是"代码"和"数据"两件事，要分别演练——回退代码不会自动还原数据。

## 成果模板

```text
线上地址 / 对应 commit 或构建号：
干净环境的构建命令 / 启动命令 / 运行时版本：
必需配置项清单（只写名称，不写值）与注入方式：
数据持久化位置（无则写"无"，并说明为什么不需要）：
另一位用户：设备/账号 | 访问到的版本 | 完成的核心任务 | 他成功的最后一步
代码回退演练：回退到哪个版本 → 页面是否恢复：
数据还原演练：还原哪份样例 → 记录数/关键字段是否回预期：
只能单向做的操作 / 恢复限制：
```

## 教学示例

教学示例：GitHub Pages 能跑本学习站这类静态模块与 hash 路由，因为它只需要返回文件；但它不会运行 Python API，也不能保存你提交的业务数据——需要持久化时得另选支持服务端的环境。另一个真实场景：部署到子路径后线上白屏，本地却正常，原因通常是资源路径写成了绝对路径 `/app.js` 而不是相对路径，浏览器去站点根目录找就 404 了。判断"上线成功"的标准是别人能打开并完成任务，不是"我本机预览没问题"。

## 常见问题

- 线上白屏：先开控制台看资源是否 404，再确认资源引用是相对路径还是站点根路径；部署在子路径（如 `/repo/`）时，写死 `/app.js` 会找不到。
- 以为恢复了代码就恢复了数据：代码回退只改程序，数据库里的记录不会自己回去。要用一次真实样例分别验证"代码回退"和"数据还原"。
- 把"命令跑成功"当成"上线成功"：构建成功只说明产物生成了；还要用另一个账号在他设备上打开、走完核心流程，才算交付。

## 交付成果

- 发布版本
- 运行与配置说明
- 备份恢复结果

## 下一步

展示真实演示，进入用户接触和交易验证。

## 完成标准

- 另一位用户能在自己的设备上访问并完成核心任务，且你能说出他成功的最后一步是什么。
- 能在干净环境按文档复现构建与启动，并能确认线上版本对应的 commit 或构建号。
- 在测试环境分别演练过"代码回退"和"样例数据还原"，恢复步骤写成别人也能照做的步骤。

## AI参与方式

- 可交给 AI：写构建与部署配置、排查资源 404、整理恢复步骤。
- 必须自己核验：干净环境按文档能跑起来；线上版本对应哪个 commit；另一位用户真的完成核心任务；代码回退与数据还原各自验证过。
- 不能交给 AI：判断"这算不算上线成功"——标准是别人能用，不是构建命令返回 0。

## 可运行起点

```text
一、先判断：静态还是需要服务端
只需要返回文件（无登录、无数据库、无密钥）→ 静态托管
需要登录 / 数据库 / 密钥 / 写入 → 服务端托管（不要用 Pages）

二、静态托管（以 GitHub Pages 为例）
1. 构建：npm run build（产物通常在 dist/）
2. 确认资源用相对路径；构建工具在子路径部署时设 base: './'
3. 按平台文档把产物发布到 Pages（分支或 Actions）
4. 用无痕窗口打开 https://<用户名>.github.io/<仓库>/
检查：控制台无 404；核心按钮能点；刷新后路由仍可用

三、服务端托管（以 Render 为例）
1. 仓库根目录写清构建命令与启动命令（如 npm ci && npm start）
2. 环境变量在平台面板配置，不写进仓库
3. 部署后先访问首页或 /health，确认 200
4. 在平台日志里找到这次访问

四、恢复演练（两步分开，别混在一起）
代码回退：回退到上一个 commit → 页面是否恢复
数据还原：还原一份样例备份 → 记录数 / 关键字段是否回预期

五、照着填（这是本任务的成果）
线上地址 / commit：
构建命令 / 启动命令 / 运行时版本：
配置项清单（只写名称）：
持久化位置：
另一位用户：设备 | 版本 | 完成的任务 | 最后一步
代码回退：从哪个版本 → 是否恢复
数据还原：哪份样例 → 是否回预期
```

## AI提示词包

```text
第一轮 · 判断托管类型（给事实，不让它拍脑袋）
我的产品：是否需要登录？是否有数据库？是否在前端用密钥？是否需要接收用户提交？
请根据这四个事实判断该用静态还是服务端托管，并说明哪一条决定了结论。
硬约束：不要推荐具体厂商，先给判断依据。

第二轮 · 生成部署配置
这是我的项目结构与构建命令（粘贴）。请只给部署所需的配置（构建命令、启动命令、需要的环境变量名）。
硬约束：不要编造平台后台步骤；不确定的地方标"按平台文档核对"。

第三轮 · 排查白屏或 404
线上打开是白屏，控制台有几条 404（粘贴）。请按可能性排序给出排查顺序，每条说明看什么证据。
硬约束：不要直接让我改代码；先给排查清单。

第四轮 · 生成恢复步骤（代码与数据分开）
这是我的部署方式与数据存储位置（粘贴）。请分别写"代码回退"和"数据还原"的步骤，并标出哪些操作只能单向做。
硬约束：不得把"回退代码"写成"数据也会回来"；每一步都要有可观察的成功标志。
```

## 成品样例

一份合格的成果长这样（示例数据，只用于对照格式）：

- 线上地址 / commit：`https://<用户名>.github.io/<仓库>/` / a1b2c3d
- 构建命令：`npm ci && npm run build`；启动命令：静态无需启动；运行时：Node 22
- 配置项清单（只写名称）：无（静态站）；服务端版会有 `VITE_API_URL`
- 持久化位置：无；数据由浏览器本地存储保存
- 另一位用户：安卓手机 / 无痕窗口 / 完成"新建并导出" / 最后一步是点"下载"
- 代码回退：从 a1b2c3d 回退到 9f8e7d6 → 页面恢复，控制台无 404
- 数据还原：还原 sample-backup.json → 记录数回到 3 条，标题一致
- 只能单向做的操作：已删除的记录无法从当前库恢复，只能从备份还原

同样的工作量，但这些**不能用**：

- 只写"构建成功，已上线"——没有线上地址、没有别人访问过
- 只回退了代码，就说"数据也恢复了"——数据库不会跟着 git 走
- 把"命令返回 0"当成验收——真正的标准是另一位用户能完成任务

## AI边界

- 可以让 AI 做：在你给出事实后判断静态还是服务端、生成部署配置、给排查 404 的顺序、写恢复步骤
- 不能让 AI 做：替你判断"是否上线成功"、替你确认另一位用户真的完成了任务、替你决定哪些恢复只能单向做
- 必须你本人判断：线上版本对应哪个 commit；配置项是否真的没进公开仓库；代码回退与数据还原是否各自演练过

## 行动步骤

### 选择与功能相符的托管

本学习站与符合规则的教学演示可用 GitHub Pages；商业交易或SaaS不能把免费Pages当业务托管。静态业务产品也要核对用途条款；业务若需服务端或数据库，选择支持该能力的环境。不要把学习站接入后端。

#### 这一步留下

托管选择与理由。

### 从干净环境构建

先删掉本机的依赖与缓存（如 node_modules），再完全按项目说明重新安装、构建、启动；记录运行时版本、必需配置项（只写名称、不写值）与持久化位置。能在一台没装过项目的机器上照做，才算可复现。配置从环境变量注入，不写入公开文件。

#### 这一步留下

可复现运行说明（版本 + 配置项清单 + 持久化位置）。

### 部署并验证真实操作

用无痕窗口或另一台设备打开线上地址，确认 HTTPS、资源全部 200（不是本地缓存）、线上版本对应哪个 commit。走一遍核心输入输出，并在平台日志里找到这次访问。已有部署沿用原平台。

#### 这一步留下

可访问版本和检查结果（资源状态 + commit + 日志位置）。

### 做一次恢复练习

在测试环境分两步演练：先回退到前一版本的代码，确认页面能重新打开；再还原一份样例数据，确认记录数量与内容回到预期。涉及数据结构改变时单独验证迁移能否回滚。把每一步的命令、期望结果和实际结果写下来，注明哪些恢复只能单向做。

#### 这一步留下

恢复记录与限制（代码回退 + 数据还原各一次）。

### 让别人接手

只给文档、不做口头补充，请同事按文档运行或检查服务。记录他问的每一个问题——每个问题都是文档缺的一句；补进文档后，再让他按更新版走一次。

#### 这一步留下

接手反馈（问题 → 文档补了哪句）。
