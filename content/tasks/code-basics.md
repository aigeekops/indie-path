# 完成一次小程序、调试与变式

## 为什么做

AI 能补充代码，但你必须有阅读、试验和纠错能力，才不被一次次整段重写困住。

## 开始条件

完成最小页面，了解输入与输出。

## 学习要点

- 变量与集合：数组存有序的项，对象存"键—值"对；`filter` 返回的是新数组，不会改动原数组——这是后面"输入不变、输出可预测"的基础。
- 函数与判断：函数把"输入 → 输出"固定成一段可复用的逻辑；`if` 分支决定哪些输入走哪条路。能说出"这个输入会进哪个分支"才算读懂。
- 调试与小步变更：一次只改一处，用"我预测的输出"对照"实际输出"；报错信息里的文件名与行号是指向问题的第一线索，先读再改，而不是整段重写。

## 成果模板

```text
运行命令 / Node 版本 / 文件路径：
三组输入 | 预期输出（长度+标识） | 实际输出 | 是否一致
出错时的完整报错首行（文件名:行号 + 错误类型）：
定位过程（打印了哪个变量、看到什么值）：
修复的是哪一行、为什么这样改：
git diff 涉及的文件与行数 / commit 号：
独立变式：换的筛选条件 | 预期条数 | 实际条数
仍无法解释的一处：
```

## 教学示例

教学示例：三条记录中两条属于项目 A，筛选后应为两条。"结果看起来合理"不如直接检查返回数组的长度与每条的标识。容易写错的是两种：一是 `filter` 的回调里忘了 `return`，结果是空数组还以为逻辑对；二是筛选时改动了原数组，导致后面再用原数据时已经不是最初那批。两者都能靠"打印长度 + 打印前两条标识"立刻发现，而不是靠肉眼判断。

## 常见问题

- 复制后不知道从哪运行：回到课程的最小运行示例，先 `node --version` 确认环境，再用 `node 文件名.js` 跑通一个文件，而不是一次贴进整个项目。
- 改了很多处才检查：把改动缩小到"一个函数、一个变化"，跑一次确认，再叠加下一个。一次改五处然后整体跑，出错时你分不清是哪一处。
- 看到报错就整段删掉重写：先读报错的第一行（文件名:行号 + 错误类型），它通常已经告诉你问题在哪一行；先定位再改，重写往往把对的也改没了。

## 完成标准

- 筛选函数在正常、空列表、缺字段三种输入下，返回的数量与每条标识都明确，且空输入返回约定结果（空数组）而不是报错。
- 能根据报错的文件名与行号定位并修复一个已知错误，并说出错误原因，而不是凭感觉改。
- 不依赖原对话、换一种筛选条件（如按状态而非按项目）也能独立完成并解释结果。

## AI参与方式

- 可交给 AI：增加一个筛选条件、解释报错含义、把改动整理成提交说明。
- 必须自己核验：先写下预测输出再运行；逐行解释 AI 改了哪几行、为什么；用 git diff 确认没有顺带改别的文件。
- 不能交给 AI：判断"这个结果算不算对"——预期必须来自需求，不能来自 AI 的实现；也不能让 AI 替你决定忽略哪条失败。

## 可运行起点

```text
一、准备环境
安装 Node.js LTS（https://nodejs.org/en/download），终端执行 node --version 确认能输出。

二、新建 records.js，先跑通再改
const records = [
  { id: "r1", project: "A", minutes: 30 },
  { id: "r2", project: "B", minutes: 20 },
  { id: "r3", project: "A", minutes: 40 }
];

function filterByProject(rows, project) {
  // 先让骨架能跑：暂时返回全部。跑一次看到"预期 2 / 实际 3"的差距，
  // 再把它改成：返回 project 匹配的【新数组】；project 为空时返回全部。
  return rows;
}

console.log(filterByProject(records, "A").length);        // 预期 2
console.log(filterByProject(records, "A").map(r => r.id)); // 预期 ["r1","r3"]
console.log(filterByProject(records, "").length);          // 预期 3
console.log(filterByProject([], "A").length);              // 预期 0

运行：node records.js

三、照着填（这是本任务的成果）
正常输入：ids = ["r1","r3"]，数量 2
空列表：数量 0，不报错
缺字段：删掉某条的 project → 记录它被排除还是报错，你的处理规则是什么
一次调试：故意把 r.project 写成 r.projct → 记下报错首行（文件:行号 + 错误类型）→ 修复
一次变式：改成按 minutes > 25 筛选 → 预期 2 条（r1、r3）→ 实际几条
```

## AI提示词包

```text
第一轮 · 只补一个函数

硬约束：不重写整个文件，不引入库，不加我没要求的参数。补完逐行解释为什么这样写。
```

## 成品样例

一份合格的成果长这样（示例数据，只用于对照格式）：

- 运行命令 / Node 版本 / 文件路径：`node records.js` / v22.x / `~/practice/records.js`
- 正常输入：预期 `["r1","r3"]`，实际 `["r1","r3"]`，一致
- 空列表：预期 0，实际 0，不报错
- 缺字段：删掉 `r2.project` 后，预期"被排除且不报错"，实际被排除，规则写进注释
- 真报错：访问 `rows[10].project` → `TypeError: Cannot read properties of undefined (reading 'project')`，指向第 7 行
- 定位过程：打印 `rows.length` 看到 3，确认 `rows[10]` 不存在，属于越界而不是字段名问题
- 静默错误：把 `row.project` 拼成 `row.projct` → 不报错，但筛选结果为空；靠"打印长度 + 标识"发现
- 修复：字段名改回 `row.project`；对越界访问加保护，说明两者为什么需要不同的排查方式
- git diff：只改 `records.js` 3 行；commit `a1b2c3d`
- 独立变式：按 `minutes > 25` → 预期 2 条 → 实际 2 条（r1、r3）

同样的工作量，但这些**不能用**：

- 只写"能跑，输出正常"——没写预期值，无法判断"正常"是什么
- 报错只写"改好了"——没有报错首行、没有定位过程，别人无法复现
- 变式是把原对话里的话再复述一遍——没有脱离原对话，也没有新的预期

## AI边界

- 可以让 AI 做：补单个函数、解释报错含义、把 diff 整理成改动清单、生成变式的实现
- 不能让 AI 做：替你决定"这个输出算不算对"、替你跳过失败的样例、替你判断哪条报错不重要
- 必须你本人判断：预期是否来自需求而不是 AI 的实现；变式是否真的脱离原对话完成；`filter` 是否真的没改动原数组

## 行动步骤

### 处理三条样例记录

先从 [Node 官方下载页](https://nodejs.org/en/download) 选择适合系统的 LTS 安装方式。打开终端或 PowerShell，进入自己的练习目录，用 node --version 确认；新建 records.js，填入本页最小输入，追加 console.log 后用 node records.js 运行。先看数组、对象、函数，再按 filter 示例写按项目筛选的函数；日期筛选放到第三步增加，空输入返回约定结果。

#### 这一步留下

可运行的小函数。

### 先预测再运行

把三组输入的预期输出先写在注释里（例如"应返回 2 条，标识为 A-1、A-3"），再运行核对。不一致时先分清是"预期写错"还是"代码错"，不把模型解释当执行结果。

#### 这一步留下

预测与实际逐条对照（含不一致时的判断）。

### 只委托一个小变化

先按 Pro Git 初始化练习仓库并提交一次基线，再让 Cursor 或 Claude Code 只增加日期筛选这一个变化。用 git status 与 git diff 核对：是否只动了预期文件、有没有顺带改动。逐行解释 AI 的修改，运行既有样例确认没打破原行为，然后单独提交这次变化；不熟悉提交身份设置时先完成书中 First-Time Git Setup。

#### 这一步留下

一个可审查变更（基线 commit + 本次 diff + 解释）。

### 独立修一次错误

在练习副本里制造两种错误，分别观察：①把 `row.project` 拼成 `row.projct`——**不会报错**，但筛选结果变成空数组，属于静默错误，只能靠"打印长度 + 标识"发现；②访问一个不存在的元素（如 `rows[10].project`）——会抛 `TypeError: Cannot read properties of undefined (reading 'project')`，读报错首行的文件与行号定位。修完后不依赖原对话、换一种筛选条件（按 minutes > 25）独立完成，确认自己不是在背步骤。

#### 这一步留下

故障记录（错误类型 + 定位过程）与变式练习。
