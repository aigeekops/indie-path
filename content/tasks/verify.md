# 用证据验收核心流程

## 为什么做

AI 可能让实现和测试共享错误理解。预期来自需求，证据来自执行，审查需要能定位到具体行为。

## 开始条件

已有可运行核心流程及测试数据。

## 学习要点

- 输入划分：按"等价类 + 边界"列输入——正常、空、无权限、重复、失败，而不是想到哪个测哪个。每类输入对应一个可预期的"应该发生什么"。
- 测试层次：单元层验证纯逻辑（规则对不对），集成层走通真实的数据读写，端到端层验证一条真实用户流程。不同层次暴露不同错误，只做一层会漏掉另外两层的问题。
- 回归与独立审查：检查要能随代码自动重跑，改完一跑就知道有没有打破旧行为；让没写过这段代码的人按需求核对，因为"自己写的错自己最容易看不见"。

## 成果模板

```text
规则 | 输入类别 | 预期（具体字段/数量） | 实际 | 检查层次 | 证据位置
测试库位置 / 运行命令 / 如何确认不是正式库：

审查发现（谁看的 / 发现的问题 / 我复现的依据）：
未验证 / 仅覆盖到的边界：
```

## 教学示例

教学示例：一条"导出报告"的接口，断言 `status === 200` 就通过了，但返回的列表里混入了他人的记录——检查全绿，数据却越权。正确的断言要核对"返回的每条记录 owner 都是当前用户"，并核对记录数量与访问范围。另一个隐蔽错误：断言"结果长度大于 0"就算过，但没核对内容是不是本次该返回的。断言要钉在真实结果上，而不是钉在"看起来没报错"上。

## 常见问题

- 全绿但实际仍错：最常见的根因是断言太宽——只断言"返回了东西""状态码不是 5xx"，没核对内容本身。把断言钉在具体字段和数量上。
- 为了过关跳过检查：保留失败并缩小调查范围，而不是删掉这条检查或改预期去迎合错误实现。检查失败是信息，不是羞辱。
- 把测试数据写进生产库：测试用的用户和记录必须隔离，运行前确认命令指向测试库，绝不让测试重置正式数据。

## 完成标准

- 至少注入一个已知错误后，对应的检查确实失败（证明检查不是摆设），恢复错误后检查通过。
- 核心任务在隔离的测试数据上实际运行通过，且整个过程中没有动用正式数据。
- 能解释关键调用的输入与输出，并在不依赖原对话的情况下改对其中一处。

## AI参与方式

- 可交给 AI：生成测试骨架、列出可覆盖的输入类别、解释某条断言为何失败。
- 必须自己核验：预期结果来自需求而非 AI 的实现；注入错误后检查确实失败；确认运行命令指向测试库。
- 不能交给 AI：判断"这个覆盖够不够"和"这条失败该不该放过"——这两件事决定验收是否可信。

## 可运行起点

```text
一、先填样例表（不写代码）
规则：导出报告只含本人记录
输入类别 | 预期（具体字段/数量） | 是否写检查
正常     | 2 条，owner 全是当前用户 | 是
无权限   | 0 条或 403 | 是（风险最高）
空数据   | 0 条，不报错 | 是
重复提交 | 只产生 1 条 | 视情况

二、最小检查脚本（不装框架，靠退出码判断）
// records.mjs
export function visibleRecords(rows, me) {
  return rows.filter(r => r.owner === me);
}

// check.mjs
import { visibleRecords } from './records.mjs';

const all = [
  { id: 1, owner: 'me' },
  { id: 2, owner: 'other' }
];
const got = visibleRecords(all, 'me');

function ok(condition, message) {
  if (!condition) {
    console.error('FAIL:', message);
    process.exit(1);
  }
}

ok(got.length === 1, '记录数量应为 1');
ok(got.every(r => r.owner === 'me'), 'owner 应全是 me');
console.log('PASS');

运行：node check.mjs
退出码 0 = 通过；非 0 = 失败。用 .mjs 是为了不依赖 package.json 的 type 配置，拷贝即跑。

三、验证检查有效（注入错误）
把 visibleRecords 里的 owner 过滤条件去掉（改成 return rows）→ 再跑 → 必须 FAIL 且退出码非 0
恢复 → 必须 PASS（退出码 0）
注入后仍然 PASS，说明检查没钉在真实结果上

四、照着填（这是本任务的成果）
测试库位置 / 运行命令 / 怎么确认不是正式库：
注入前后：改哪一行 → 哪条失败 → 恢复后通过
断言钉在：字段 owner + 数量
审查发现：谁看的 / 发现什么 / 我复现的依据
未验证 / 仅覆盖到的边界：
```

## 成品样例

一份合格的成果长这样（示例数据，只用于对照格式）：

- 规则：导出报告只含本人记录
- 正常：预期 2 条且 owner 全是 me；实际 2 条，通过
- 无权限：预期 403；实际 403，通过
- 空数据：预期 0 条不报错；实际 0 条，通过
- 测试库确认：运行前打印 `DB=records_test`，确认不是正式库
- 注入错误：注释掉 owner 过滤 → 该条检查失败（1 条变 2 条）→ 恢复后通过
- 断言钉在：返回数组长度 + 每条 owner 字段
- 审查发现：同事指出"重复提交没覆盖"；我复现后确认是真缺口
- 未验证：并发提交、跨租户数据

同样的工作量，但这些**不能用**：

- 只断言 `status === 200`：越权数据混进来也能通过
- 注入错误后仍然全绿：说明检查是摆设
- 为了让检查通过改预期：把"2 条"改成"大于 0 条"，等于放弃验证

## AI边界

- 可以让 AI 做：生成检查骨架、列输入类别、解释某条失败、审查覆盖缺口
- 不能让 AI 做：替你判断"这条失败该不该放过"、替你改预期迎合实现、替你确认测试库是不是正式库
- 必须你本人判断：预期是否来自需求；注入错误后检查是否真的失败；审查发现能不能复现

## 行动步骤

### 先写样例后看实现

从需求而不是从实现出发，列出五类输入：正常、空输入、无权限、重复、失败。对每一类先写下"应该发生什么"（预期结果），再决定哪些值得写检查——按风险排，不凑数量。例如"无权限的用户能否看到他人记录"比"正常用户能看到自己的"风险更高，应优先覆盖。

#### 这一步留下

验收样例表（输入类别 + 预期结果 + 是否写检查 + 理由）。

### 隔离数据并执行

运行前先确认命令连的是测试库而不是正式库（打印当前环境或库名）。逻辑规则在逻辑层验证，真实数据读写经过组件，至少走通一条真实用户流程。准备可重复的测试数据（固定 ID），让每次运行结果可比。

#### 这一步留下

测试库确认 + 检查命令与输出。

### 验证检查有效

在练习分支去掉一个关键条件，检查应失败；恢复后应通过。若没失败，修正检查。

#### 这一步留下

已知错误被发现的记录。

### 独立审查差异

把需求和 diff 一起交给没写过这段代码的同事，先不给你的结论。请他指出"哪里可能不符合需求"，你逐条复现：能复现的记为问题，复现不了的记为猜测。AI 可以帮你列线索，但不能替你判定问题成立。

#### 这一步留下

审查结果（问题/猜测分开）与待验证项。
