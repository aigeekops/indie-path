# 完成一个可以操作的界面

## 为什么做

界面生成很快，但用户是否看懂输入、状态与结果，仍需要观察。先连接真实流程，再优化视觉。

## 开始条件

已确定流程与接口约定；服务端可先独立验证。

## 学习要点

- 组件与状态：界面是"状态 → 视图"的映射。用户输入改变状态，视图随之更新，而不是手动去改某个 DOM 节点。能说清"这个界面此刻由哪几个状态值决定"才算读懂。
- 表单校验：校验在提交前拦截非法输入，并保留用户已经填的内容，不让其全部重填；校验失败要指出具体哪字段有问题。
- 异步与错误反馈：一次请求有"进行中 / 成功 / 失败"三种结果。失败时要把原因说给用户听（而不是默默空着），并且界面在失败后仍能继续操作，不会卡在转圈。

## 成果模板

```text
页面/主动作/关键组件文件：
输入字段 | 校验规则 | 校验失败时保留了哪些已填内容：
写入请求：方法/URL/请求体字段/响应状态 → 读取请求：URL/返回条数
四状态触发方式与表现：正常/加载/空结果/失败各一句
失败后是否还能继续操作 / 重复点击是否被拦截：
刷新后从服务端重读到的条数：
导出或打印的实际产物（文件名/页数/格式）：
试用：日期 | 任务说明 | 是否提供了帮助（具体帮了什么）
本轮修改 / 待再次观察：
```

## 教学示例

教学示例：写入接口返回 200 后，再把响应里的记录写回界面状态，用户才能在"我的列表"里看到它；如果只是把记录塞进本地 state 假装成功、没有真正发写请求，刷新后内容就消失——这不叫完成。另一个常见错误：一个导出按钮看起来漂亮，点下去却没接上任何生成逻辑，只是装饰。判断的标准是"失败或刷新后数据还在不在、能不能真的用"，不是"好不好看"。

## 常见问题

- 永远只看到成功状态：用开发者工具的 Network 节流（Slow 3G）构造"进行中"，把接口临时指向错误地址或断网构造"失败"，用空账号或清掉数据构造"空结果"。三种状态都要能演示，而不是只在代码里写个分支。
- 直接生成整站后不会改：回到"一页一条主流程"的最小界面，先把写入和读取跑通，再叠加状态与校验，不要一次让 AI 生成整套页面再从头读。
- 校验把用户已填内容清空：校验失败时只标红出错的字段，保留其他字段的值；刷新或重提交不要让用户从头再填。

继续双账号权限与可用性检查；已有界面可用成果确认。

## 完成标准

- 界面的读取与写入都走真实接口（不是假数据），且写入后刷新页面能从服务端重新读到刚保存的内容。
- 在慢请求、空结果、失败三种情况下界面各自有明确表现，且失败后用户仍能继续操作（不会卡死在转圈）。
- 能解释从"用户点击"到"界面更新"之间，状态经历了哪几个变化（如 loading → success / error）。

## AI参与方式

- 可交给 AI：搭表单与状态骨架、生成四种状态的 UI 分支、把接口返回映射到界面。
- 必须自己核验：写入后刷新能否从服务端读回、失败时是否保留输入且能继续操作、导出的文件是否真的能打开。
- 不能交给 AI：判断"用户看懂没有"——这必须靠观察真实用户；也不能让 AI 用假数据把失败状态盖过去。

## 可运行起点

```text
一、先确认接口真的在（不要先写界面）
curl -i http://127.0.0.1:3000/records
curl -i -X POST http://127.0.0.1:3000/records -H "Content-Type: application/json" -d '{"title":"测试"}'
两条都返回 2xx 且能看到数据，再开始界面。返回 404/500 先修接口。

二、页面骨架（index.html）
<form id="form">
  <label for="title">标题</label>
  <input id="title" name="title" required maxlength="60">
  <p id="error" role="alert"></p>
  <button id="submit" type="submit">保存</button>
</form>
<p id="status" aria-live="polite"></p>
<ul id="list"></ul>
<script src="app.js"></script>

三、状态机（app.js）
const API = {
  list: () => fetch('/records').then(r => r.ok ? r.json() : Promise.reject(r.status)),
  create: (data) => fetch('/records', {
    method: 'POST',
    headers: {'Content-Type': 'application/json'},
    body: JSON.stringify(data)
  }).then(r => r.ok ? r.json() : Promise.reject(r.status))
};

// 四个状态，逐一在 render(state) 里写清楚：
// idle    可以提交，按钮可用
// loading 按钮禁用，status 显示"保存中…"
// empty   list 显示"还没有内容"
// error   error 显示可读原因，输入框保留已填内容，按钮恢复可用

四、四种状态怎么构造（不能只在代码里留分支）
成功：正常提交一条
加载中：DevTools → Network → 节流 Slow 3G
空结果：清空数据或换新账号
失败：把 API 地址临时改成 /records-x

五、照着填（这是本任务的成果）
写入请求：POST /records | 201 | 返回 id
读取请求：GET /records | 200 | 返回 1 条
刷新后条数：1
失败后输入是否保留：是
导出产物：文件名/页数/格式
试用：日期 | 任务说明 | 是否提供帮助
```

## AI提示词包

```text
第一轮 · 只搭表单与状态骨架
我的字段是 title（必填，最长 60），有一个提交按钮和一个列表。
请只给表单 HTML 与 render(state) 的骨架，状态有 idle/loading/empty/error。
硬约束：先不接接口，不写样式，不生成整站；每个状态用一句注释说明界面表现。

第二轮 · 补错误处理
这是我的 API 封装（粘贴）。请列出所有可能的失败路径（网络失败、非 2xx、响应不是 JSON、超时），逐个说明当前代码会怎样、用户会看到什么。
硬约束：不要直接重写，只列缺口；每条缺口给出最小修法。

第三轮 · 只改一个失败状态
用户提交后接口返回 500。请只改 error 分支：显示可读原因、保留输入、按钮恢复可用。
硬约束：不要动成功路径；给出后说明怎么用 DevTools 复现这次 500。

第四轮 · 生成导出并说明降级
把列表导出为一种固定格式（先用打印另存 PDF 或纯文本下载）。
请给最小实现，并说明在不支持打印或下载的环境里降级成什么。
硬约束：不引入文档库，不新增依赖。
```

## 成品样例

一份合格的成果长这样（示例数据，只用于对照格式）：

- 页面：一页一条主流程；表单在上，列表在下
- 输入字段：title（必填，≤60）；失败时保留已填的 title
- 写入请求：POST /records → 201，返回 `{id:"r1",title:"测试"}`
- 读取请求：GET /records → 200，返回 1 条
- 四状态：正常显示列表；加载中按钮禁用并显示"保存中…"；空结果显示"还没有内容"；失败显示"保存失败（500），请重试"并保留输入
- 失败后：按钮恢复可用，可以再次提交
- 刷新后：从服务端重读 1 条
- 导出：`record-2026-10-26.txt`，1 条，UTF-8
- 试用：10-26 / "把记录导出给客户" / 提供了帮助：指出导出入口

同样的工作量，但这些**不能用**：

- 只做了成功态：加载时按钮还能连点，失败时页面一片空白
- 用本地 state 假装保存：刷新后内容消失，根本没有发写请求
- 导出按钮只是装饰：点了没反应，或下载的是空文件

## AI边界

- 可以让 AI 做：搭表单与状态骨架、生成四状态分支、把接口返回映射到界面、给导出的最小实现
- 不能让 AI 做：用假数据把失败状态盖过去、替你判断"用户看懂没有"、替你决定失败时是否保留输入
- 必须你本人判断：写入后刷新能否从服务端读回；失败后是否还能继续操作；导出的文件能否真的打开

## 行动步骤

### 复用熟悉的界面技术

未独立做过界面时，先按 HTML/CSS 示例做最小页面，再用 JavaScript 的数组、对象、函数和 filter 写一个筛选。能解释后再按 React 示例建立组件；已有 Vue 等界面经验直接做同等行为，不更换整套技术。

#### 这一步留下

最小界面入口。

### 做输入与预览

先用教学样例完成表单和预览，明确标记样例。增加必填校验，保留用户输入。

#### 这一步留下

可操作表单。

### 连接真实接口

先不用界面，直接用 curl 或浏览器地址栏打一次接口，确认它真的返回数据（状态码 + 一条样例）。再读接口约定，接到界面：先用写入请求保存，再用读取请求刷新预览。把预览内容导出为一种固定格式（例如文本文件）；先用打印页面另存 PDF 或浏览器已有下载能力，不引入复杂文档格式。对照 Network 里的请求与响应，不用假数据遮住失败。

#### 这一步留下

真实主流程（含一次脱离界面的接口验证）。

### 补四种状态

为正常、加载中、空结果、失败四种情况各写一种界面表现：加载中给明确提示且不允许多次重复提交；空结果显示"还没有内容"而不是一片空白；失败显示可读原因并保留已输入内容。用开发者工具分别构造这四种（Slow 3G 模拟加载、空账号模拟空结果、错误地址模拟失败），逐一确认，而不是只在代码里留个分支。重复点击时按约定处理，错误后要能继续操作。

#### 这一步留下

四状态检查表（每种状态的触发方式与界面表现）。

### 请用户试做

给目标，不逐步指导。用户操作时记录三类问题：理解错（以为要做别的事）、重复操作（点了又点）、输出问题（导出打不开或格式不对）。只改首要卡点，其余留到下一轮。

#### 这一步留下

一次试用修订（问题分类 + 改的那一处）。
